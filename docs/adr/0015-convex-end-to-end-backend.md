# 15. Convex as the backend, end to end

- Status: Proposed
- Date: 2026-11-17
- Supersedes: ADR 0009 (D1 and Drizzle), ADR 0010 (no KV), ADR 0013 (local-first storage)
- Amends: ADR 0003, 0005, 0011 and 0012 (see Changes to earlier ADRs)

## Context

The plan was Cloudflare D1 for data (ADR 0009), Better Auth for accounts (ADR 0008), and conversations kept in the browser (ADR 0013), synced to D1 later (#36). Sync was the hardest open problem on the roadmap: ADR 0013 lists conflicts between devices that append offline, deletions that reappear on the next pull, which local conversations belong to which account, and merging titles.

The maintainer decided on 2026-11-17 to use Convex for the whole backend instead, to drop browser storage, and to require Google sign-up before the first chat (ADR 0016). No one uses the app yet, so nothing needs migrating.

What we checked (all read 2026-11-17):

- **Limits** ([Convex, "Limits"](https://docs.convex.dev/production/state/limits)): documents up to 1 MiB; function arguments and return values up to 16 MiB (Node actions: arguments up to 5 MiB); queries and mutations 1 second of user code; actions 30 minutes in the Convex runtime with 64 MiB of memory, 10 minutes in the Node runtime with 512 MiB. "Subscription updates" count as function calls. Each action keeps at most 1,024 log lines.
- **HTTP actions** ([Convex, "HTTP Actions"](https://docs.convex.dev/functions/http-actions)): a response body can be a `ReadableStream` (the page recommends it for large responses; it shows no streaming example and does not mention server-sent events). Responses up to 100 MiB. HTTP actions are not retried. CORS is the handler's job. The page does not say which time limit applies to HTTP actions, or whether one keeps running after the client disconnects.
- **Logs** ([dashboard logs](https://docs.convex.dev/dashboard/deployments/logs), [log streams](https://docs.convex.dev/production/integrations/log-streams)): the dashboard shows a function's log lines and exceptions. The log stream schema records the _size_ of a function's arguments, "Absent for HTTP actions", and has no field for HTTP headers or bodies. Neither page says argument contents are logged, nor that anything is redacted.
- **TanStack Start** ([Convex, "TanStack Start"](https://docs.convex.dev/client/react/tanstack-start)): the recommended integration is through TanStack Query (`@tanstack/react-query` 5.102.0 or later); `useSuspenseQuery` renders on the server and the browser resumes live subscriptions. The page notes TanStack Start "is in Release Candidate". Server-side auth guides exist for Clerk and WorkOS only.
- **Regions** ([Convex, "Regions"](https://docs.convex.dev/production/regions)): `aws-us-east-1` at standard price; Ireland, Sydney and Canada at a 30% surcharge. "An existing deployment's region cannot be changed."
- **Pricing**: see Cost below.

## Decision

Built: the Convex project and deploy (#35), accounts (#34, ADR 0016), storage (#74, see "Built in #74" below) and the chat move (#75, see "Built in #75" below): the interview runs in a Convex HTTP action, which writes each run to the idea's turn document.

### What runs where

- **Convex** holds all application data and all server logic: ideas and messages, accounts (ADR 0016), and the model call that runs the interview.
- **Cloudflare Workers** keeps serving the TanStack Start app: server-rendered pages and static assets, as today (ADR 0005). It has no API routes, no database and no secrets of its own once the chat route has moved. Convex does not host TanStack Start's server rendering.
- The browser talks to Convex directly, through Convex's TanStack Query integration.

### Content-Security-Policy

Today `connect-src` is `'self'` (`features/security/csp.ts`), and `docs/internals/byok-and-secrets.md` forbids adding a host. `connect-src` restricts the URLs that script interfaces such as `fetch` and `WebSocket` can load ([CSP Level 3](https://www.w3.org/TR/CSP3/#directive-connect-src), read 2026-11-17). It does not restrict top-level navigation, so an injected script that can read a key could still send it elsewhere in a navigation URL. The policy narrows where a key can go; preventing script injection (ADR 0003, rule 5) remains the main defence. Convex is a different origin, so the browser cannot reach it under the current policy.

- **Decision: allow exactly our own Convex deployment, nothing else.** `connect-src` will list `'self'` plus that deployment's two origins: its client URL (`https://` and `wss://` on `<deployment>.convex.cloud`, for queries, mutations and live updates) and its HTTP actions URL (`https://<deployment>.convex.site`, where the key goes). The names come from build configuration. No wildcard such as `*.convex.cloud`, which would let a script send a key to someone else's Convex deployment.
- The rule's purpose stays the same: the page's connections, and so the key's documented path, go only to our own backend, now running on Convex, and from there only to the provider the user chose.
- **Rejected: proxying Convex through the Worker.** Live updates use a WebSocket, so the Worker would carry every sync message and return as a moving part, which is what this ADR removes.
- The CSP change lands with the first PR that connects the browser to Convex (#35), together with every description of the policy: the rule in `docs/internals/byok-and-secrets.md` and the CSP sentence in `.github/SECURITY.md` ("connections only to our own origin"), so no document describes a policy the code no longer has. The description of where the key goes (ADR 0003 and the key section of `SECURITY.md`) changes later, with the chat move, because that is when the key starts going to Convex.

### No browser storage of conversations

IndexedDB storage (ADR 0013) is removed, with `idb`, `fake-indexeddb`, the BroadcastChannel hint and the `persist()` notice. Data already in browsers is dropped without a notice (no users yet). There is no offline mode: every turn needs the model API anyway. Provider keys stay in the browser exactly as ADR 0003 describes; that store is unrelated.

### Data model

- One document per **idea** (the conversation: owner, title, status, timestamps) and one per **message**, keyed by idea and `seq`. One message per document keeps each well under the 1 MiB limit, which a whole conversation in one document could outgrow.
- ADR 0012 still holds: messages are the source of truth, the tree is derived by `deriveTree`, `seq` is the only order, and messages are append-only. The `nextSeq` and `titleRev` checks of ADR 0013 become checks inside Convex mutations, which run as transactions.
- **Only final messages become message documents.** The finality rule of ADR 0013 and its #28 notes stays: a message is final when it will no longer change. That means user messages, assistant messages whose tool calls all have an answer (the answer is stored with the message, ADR 0012), and a closing reply once its run has finished. The savable-prefix logic decides this, as it does today.
- **Everything not yet final lives in one turn document per idea.** This covers a reply that is still streaming, and a round or finish proposal waiting for the user's answer. Message documents are never edited; a message moves from the turn document to a message document only by being appended at `seq = nextSeq …` in the same mutation that clears the turn document. That happens:
  - when the user answers a round or finish proposal (the answered message becomes final);
  - when a run ends with a closing reply that needs no answer, in the mutation that ends the run.

  A failed or stopped run is never appended.
- **One run per idea, owned by a run id.** A turn document has one of three statuses: `running` (the action is streaming), `waiting` (the run ended with a round or finish proposal that needs the user's answer) and `interrupted`. Starting a run is a mutation that writes a new run id, `running` and a last-write time.
  - **Batch writes and the end-of-run mutation** require the same run id **and** `running`, in the same transaction. A run that resumes after its turn was marked `interrupted`, or after another run took over, is rejected and writes nothing. The end-of-run mutation either appends a closing reply and clears the turn, or sets `waiting`.
  - **The answer mutation** requires `waiting` and the run id the user is answering, and check `nextSeq` where it appends.
  - A new run may start only when there is no turn, or the turn is `interrupted`; a second tab or a Try again cannot start one while another run owns the turn.
- **Marking a run interrupted does not rely on the action.** If the action fails or is stopped, it will mark the turn `interrupted` itself, with the same guard as its other writes (its own run id and `running`), so a failing stale run cannot interrupt a newer run's turn. If it dies without doing so, a scheduled check will. The start mutation schedules a check mutation, with only the idea id and run id as arguments, never the key. When it runs:
  - if another run owns the turn, or the turn is no longer `running`, it does nothing and does not reschedule;
  - if the same run owns the turn and has not written for a set time, it marks the turn `interrupted`;
  - otherwise the run is still active, and it schedules itself again for the set time after the run's last write.

  So a live run always has one pending check, and a run that dies is marked within about the set time after its last write. The time will be chosen when this is built, above the longest normal gap between batches. Try again will be offered only for an `interrupted` turn, and will replace it with a new run.
- Documents hold only what the app needs. Provider keys never appear in any document, argument or log (ADR 0003).
- Schema changes are backward compatible, as ADR 0009 required for D1: add a field before code uses it, migrate data, then remove the old field only when nothing reads it, because the previous release's code may run against the new schema during a deploy.

### The interview runs in Convex

- The model call moves from `routes/api/chat.ts` to a **Convex HTTP action** that streams the reply to the browser, as the Worker route does today.
- **The key arrives in a request header, never as a function argument.** An argument to a scheduled function is stored in Convex until the job runs, and an ordinary argument is a value we would have to keep out of every log and error by hand. The log stream schema has no field for HTTP headers. So the browser calls the HTTP action with the key in the `x-byok-<provider>` header, and the action never passes the key to `ctx.scheduler`, `ctx.runMutation`, `ctx.runAction` or a log line.
- The action checks that the caller is signed in and owns the idea before calling the model, and writes the reply to the idea's turn document (see Data model) as it streams, in batches rather than per token.
- Every rule in `docs/internals/byok-and-secrets.md` carries over: the safe logger, the library logger override, fixed error strings, scrubbed `RUN_ERROR` chunks, the sentinel key test and the lint rules. ADR 0003 and `SECURITY.md` are updated in the PR that moves the route.

### Where the code lives

Decided on 2026-11-18, while building #35. The Convex functions and schema live in their own workspace package, **`packages/backend`** (`@unfold/backend`, with its `convex/` folder), not inside `apps/web`.

- A native app (Expo) is planned. The decision is that every app uses **one shared backend package and the same production deployment**, so an idea started on one device is there on the other, and every app depends on `@unfold/backend` for the generated API and types. A `convex/` folder per app would mean two sets of schema and functions to keep in step. Each `convex deploy` pushes one folder's "functions, indexes, and schema" to the deployment chosen by the deploy key ([Convex, "`npx convex deploy`"](https://docs.convex.dev/cli/reference/deploy), read 2026-11-18), so two folders would either need two deployments, and so two databases, or take turns overwriting one deployment's schema.
- It is a package rather than an app because it has no pages; it is deployed with the Convex CLI from its own folder. Convex's monorepo template has the same layout: "`apps/web`", "`apps/native` - the Expo native app" and "`packages/backend` - the Convex backend and generated API types" ([get-convex/turbo-expo-nextjs-clerk-convex-monorepo](https://github.com/get-convex/turbo-expo-nextjs-clerk-convex-monorepo), README, read 2026-11-18).
- This is an exception to the rule that a package waits for a second consumer (`AGENTS.md`): the backend is not shared helper code, and moving it after the auth, storage and chat moves would touch every import, the CI check and the deploy.
- Rejected: `apps/web/convex` now and a move later (the cost above), and `apps/convex` (works, but less common for code other apps import).

### Deployment

- One production Convex deployment, in **`aws-us-east-1`** (standard price; the region cannot be changed later), plus one development deployment per developer or a local backend.
- On release, Convex functions deploy **before** the Worker, so new pages never call functions that do not exist yet. The deploy key is a secret in the `production` GitHub environment, set by the maintainer, never in chat.

### Built in #74 (storage)

Recorded on 2026-11-19, while building the storage move.

- **Ideas keep their browser-made id.** An idea has a `clientId` (the UUIDv7 the browser already makes) with its own index, and addresses stay `/c/<clientId>`. The screen gives a new idea its address on the first save without remounting the chat, which needs the id before the save returns; a Convex `_id` would arrive only after it.
- **A message is stored as JSON text** (`message: v.string()`), not as a Convex object. A `UIMessage` can hold a `Date` and keys that Convex does not allow as field names. The append mutation checks that each one parses, has an `id`, a known `role` and `parts`, and is at most 512 KiB.
- **The turn document waits for #75.** While the chat runs on the Worker, the server never holds a message that is not final: the browser keeps it, as before. The turn document, run ids and statuses were built in #75, before the HTTP action that writes them; the notes are in `convex/turns.ts`:
  - The writes of a run (`start`, `batch`, `end`, `interrupt`) and the scheduled `check` are internal mutations, so only the action can call them; the action passes the signed-in user's id to `start`. The owner's calls are `get` (live), `answer` and `stop`. Stop marks a running or waiting turn `interrupted`; a running action sees it at its next write, which returns false. Stopping a waiting turn abandons its question, which is also the way out if an answer is too large to store. `end` checks the idea's limits before it sets `waiting`, so a run never waits for an answer the idea cannot hold.
  - The turn holds the whole message as JSON text, replaced at each batch, as message documents do.
  - A turn goes stale after `RUN_STALE_MS` (90 seconds) without a write, and the action, when it is built, must write at least every `RUN_HEARTBEAT_MS` (30 seconds), even with nothing new, so a model that is slow to start is not mistaken for a dead run.
  - `ideas.append` is refused with `busy` while a turn is `running` or `waiting`, so no message lands under a run that did not see it. An interrupted turn does not hold the idea. Deleting an idea deletes its turn.
- **The list of ideas is a live query** through `@convex-dev/react-query`, so a change in another tab or on another device shows up without the BroadcastChannel hint. One-off reads and writes go through the existing `ConversationStore` seam.
- **An idea holds at most 8 MiB and 4,096 messages** (`MAX_IDEA_BYTES`, tracked in `ideas.bytes`, and `MAX_IDEA_MESSAGES`). `load` returns every message and `remove` reads and deletes every message, each in one call. Convex caps a call at 16 MiB read and returned, an array at 8,192 elements, and a transaction in documents read and written; the caps keep both possible for any idea. An interview is a few hundred KiB, so the cap is thousands of turns. A save past it is refused, and the app says the conversation is not saved. Paging both reads would remove the cap, if ideas ever need to be larger. One write carries at most 100 messages; the browser splits a longer queue.
- `ownerId` became `v.id("users")` and `message` became a string. Neither is backward compatible in general, but no function had written either table, so no document existed to break.

### Spike for #75 (the chat move)

Recorded on 2026-11-19. A throwaway HTTP action, never merged, on local Convex backends (`convex` 1.50.0, `@tanstack/ai` 1.3.0, `@tanstack/ai-anthropic` 1.1.1), with aimock in place of the provider and a fake key. **Everything below was seen on a local backend only.** A cloud deployment may differ in time limits and disconnect handling; those are checked on a cloud development deployment before the first release that includes the move (merging to `main` deploys nothing; a release does, ADR 0005). Error redaction differs between development and production deployments by design, so it is checked on production (see the last bullet of Consequences).

- **`chat()` runs in the default Convex runtime.** The action imported `@tanstack/ai`, the Anthropic adapter, the app's `SYSTEM_PROMPT` and `interviewTools`; the push bundled them with no `"use node"`. That matters because an HTTP action cannot run in the Node runtime, and a Node action cannot stream a response.
- **Streaming works.** `toServerSentEventsResponse(...)` returned from the HTTP action reached the client chunk by chunk as the provider sent them (about 250 ms apart with a 250 ms fixture delay), not buffered. The E2E interview fixture, with its `ask_round` tool call, streamed the same event types as on the Worker.
- **The action outlives the client, if we let it.** With `request.signal` forwarded to `chat()`'s `abortController`, a disconnect stopped the run within milliseconds (the backend logs `Client disconnected` and the signal fires). Without it, a run whose client left after 2 to 3 seconds kept going and wrote the whole reply: a 28-second reply in full, and a 7-minute one (430 s) in full. So the action must **not** forward `request.signal`; Stop becomes a mutation that ends the run, which the next batch write sees.
- **An aborted `chat()` ends quietly.** When aborted, the stream simply finishes; nothing is thrown, and the spike's run was recorded as `done`. The action must check its abort state itself and mark the turn `interrupted`, never treat the end of the stream as success.
- **Uncaught errors reach the client in full on a local backend.** A thrown error in an HTTP action returns a JSON body with the error message and a server stack trace, and an error thrown inside a mutation called from the stream surfaced as a `RUN_ERROR` chunk with the mutation's message. Convex's docs say that on a production deployment "any server error will be redacted to only include the name of the function and a generic "Server Error" message", that application errors (`ConvexError`) keep their custom `data`, and that development deployments return the original message and stack trace ([Convex, "Error Handling"](https://docs.convex.dev/functions/error-handling), read 2026-11-19). The page does not mention HTTP action responses. The action will catch everything and return fixed strings, as the Worker route does, and never put conversation text or provider messages in a `ConvexError`'s data; scrubbing `RUN_ERROR` stays.
- **Auth works with the access token as a bearer header.** `ctx.auth.getUserIdentity()` returned the Convex Auth v2 user for `Authorization: Bearer <access token>`, and `null` with no header. A malformed token makes `getUserIdentity()` **throw** (and so leak a message, as above); the action will catch it and answer 401. The browser gets the token from `useAuthToken()` (`@convex-dev/auth/react`).
- **The key was not stored or logged.** After all runs, the fake key appeared nowhere in the local backend's SQLite database (documents, scheduled jobs, storage) or its log output.
- **Batching and cost.** Writing the turn at most every 500 ms gave 54 batch mutations for a 28-second reply (111 chunks), and a tab subscribed to the turn received 57 updates: about one live-query re-run per batch per open tab. A short reply with a tool call was 1 batch and 4 updates. So one reply costs roughly `2 + batches × (1 + open tabs)` function calls, plus the HTTP action and the CORS preflight if those count (the limits page lists "explicit client calls, scheduled executions, subscription updates, and file accesses"; it does not mention HTTP actions or preflights). The batch interval is the main cost lever: 1 to 2 seconds keeps a typical reply to a few dozen calls. Action compute: the limits page prices the Convex runtime at "$0.16/GB-hour CPU time" with 64 MiB, which suggests waiting on the model is not billed, but no page says so. Both will be measured on the cloud development deployment.
- **CORS is ours.** The app and the HTTP action are different origins. A chat request sets the custom `x-byok-anthropic` header, so it is not a CORS simple request and the browser preflights it ("since a custom header is set, this request is preflighted", [MDN, "Cross-Origin Resource Sharing"](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)). A preflight result is cached only for `Access-Control-Max-Age`, which defaults to 5 seconds; Chromium caps it at 2 hours and Firefox at 24 hours ([MDN, "Access-Control-Max-Age"](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Max-Age)). Both read 2026-11-19. The action will answer `OPTIONS` with exactly the app's origins and will set `Access-Control-Max-Age`, so a tab can reuse one preflight across many turns instead of sending one per turn.
- **Time limit.** Not found locally (7 minutes ran fine). The docs disagree: the limits page says 30 minutes for the Convex runtime, the actions page says actions time out after 10 minutes, and neither names HTTP actions. An interview reply is well under either; the scheduled check covers a run cut off at the limit.

### Built in #75 (the chat move)

Recorded on 2026-11-19. Everything below was run on a local Convex backend with aimock, except the cloud measurements in the last item.

- **Where the code is.** The interview protocol (tools, system prompt, providers, round answers, `deriveTree`, outline) moved to a platform-neutral package, **`packages/interview`** (`@unfold/interview`), because the backend now needs it and the planned native app will too; it has no DOM, React or server code. The server-only code (`convex/chat/handler.ts`, `safeLog.ts`, `testProviderUrl.ts`) and the route (`convex/http.ts`, `POST /chat` and its `OPTIONS` preflight) live in `packages/backend`. Convex module paths allow only letters, digits, underscores and periods, so the files are camel-cased. The Worker's `/api/chat` route is deleted.
- **What the action does.** It signs the caller in from the bearer token (401 if missing or malformed), reads the idea id from the request, claims the idea's turn with `turns.start` (404 for an idea that is not the caller's, 409 while another run owns it), and streams the reply to the browser while writing it to the turn document at most every 1.5 s, with a heartbeat at `RUN_HEARTBEAT_MS`. It ends the run with `turns.end` (a closing reply is appended; a round or finish proposal makes the turn `waiting`) or marks it `interrupted` when the model fails, the turn was stopped or taken, the idea cannot hold the message, or the stream was aborted.
- **It outlives the browser.** The handler pulls the model's stream by hand, so when the browser stops reading, the run carries on recording until the model is done. This is tested with a fake model in a unit test (`tests/chat-turns.test.ts`), not on a running backend; the spike saw the same on a local backend with its own code. A cloud development deployment saw it too, with caveats (see the measurements below). It is not tied to `request.signal`; only a lost turn or a failure aborts it. Stop is the `turns.stop` mutation, which the next batch write sees.
- **The browser** sends the idea id, the outline, `expectedNextSeq` and `expectedLastMessageId` in `forwardedProps`, the access token in `Authorization` (`useAuthToken`) and the key in `x-byok-anthropic`. The action's address is the site origin the CSP allows, inferred from a `*.convex.cloud` client URL when `VITE_CONVEX_SITE_URL` is not set (`convexSiteUrl`).
- **Before each request the saver (`ConversationSaver.beforeRun`) brings storage up to the messages being sent**, because `ideas.append` is refused while a turn is running or waiting:
  - it creates a new idea, but never recreates one that was stored and is gone (deleted elsewhere: a `deleted` conflict);
  - it stores the answer to the waiting run with `turns.answer`, and abandons a waiting question the tab no longer has, passing the stored count it checked so `turns.stop` refuses with a conflict if another tab stored messages since;
  - it skips a reply without a question at the end of the list: the action stores complete ones, so that one was stopped or failed and is never stored, and Try again can continue past it. One anywhere else fails the save;
  - it appends the rest (the user's messages, or an answered question whose turn was abandoned);
  - it refuses, as a `changed` conflict and before it stops or writes anything, when storage holds another history than the tab: more messages, or as many with another last message (`ideas.get` returns the last message's id). Another tab or device moved on.
- **It resolves with the stored history, which the request carries as `expectedNextSeq` and `expectedLastMessageId`.** `turns.start` refuses the run (`conflict`, answered 409 `history_conflict`) unless the idea holds exactly that many messages and its last one has that id. Messages are append-only and their ids unique, so the two identify the history, and a reply is never appended after history the model did not see. If storage fails the request is not sent.
- **Stop** calls `turns.stop`, queued with the saver's writes so a request sent right after waits for it. The request may still be on its way to the action, so Stop looks for the run for about 3 seconds. If the server cannot be reached or no run turns up, the stop is kept and applied before the next write. Not covered: a request that reaches the action after that next write; Stop does not mark the idea on the server.
- After the request starts, the action writes everything the model says, so the browser no longer saves from the stream (the savable-prefix logic is removed).
- **Not built.** A reload while a run is streaming or a question is waiting does not yet restore it from the turn document: the browser still loads only stored messages, and the abandoned question is stopped when the user continues. Showing the live turn (and Try again for an `interrupted` one) is follow-up work.
- **Measured on a cloud development deployment** (`dev/pragyan`, `calculating-warbler-958`, US East like production; 2026-11-19). The batch interval is 1.5 s, inside the 1 to 2 s the spike suggested.
  - **How.** The maintainer had no Anthropic key, so the model was a fake: a temporary HTTP action on the same deployment that streamed an Anthropic-style reply of a set length and speed, reached through `UNFOLD_TEST_PROVIDER_URL` with the loopback check relaxed for that host only. A Node script played the browser: it signed in with the test-only password method, created an idea, called `POST /chat` with the browser's request shape, and kept the sidebar's live `ideas.list` subscription open, as one tab does. Counts come from the deployment's function logs (`convex logs --success --jsonl`) and `convex deployment usage`. The fake route, the relaxed check and the password switch were removed afterwards and the deployment's code is `main` again. **Not run: a real model and a real browser.** Repeat the four replies with a real key once a second provider lands (Gemini is not supported yet); the counts below should hold, but a real model adds time to the first token and may add heartbeats.
  - **What counts.** The 399 executions in the logs matched the 400 function calls in the usage counter (one missed by the log capture): every execution is a call, including the HTTP action itself, a CORS preflight (also an HTTP action), each `runQuery` and `runMutation` from the action, scheduled checks, live-query re-runs, and cached query results.
  - **One reply, function calls.** A short reply (1.3 s) cost **6**: the HTTP action, the session query `getAuthUserId` runs, `turns.start`, `turns.end`, the scheduled `turns.check` (which then does nothing) and one `ideas.list` re-run per open tab. A 30-second reply cost **26**: the same plus 20 batches. A reply stopped after 7 s cost 10 plus the browser's `turns.stop`, and no list re-run (nothing was appended). So a reply costs about `5 + duration / 1.5 s + duration / 90 s + open tabs`, plus the browser's own write before it (`ideas.create` or `append`, with its list re-run) and a preflight at most every 2 hours per tab. Batches do not re-run `ideas.list` (they only touch the turn document); a tab that subscribes to `turns.get` would add one re-run per batch.
  - **One reply, action compute.** Billed as 64 MiB times the action's recorded wall-clock time, waiting on the model included: the usage counter (`actionComputeConvexGbHours`, 0.04552 GB-hours) matched the summed execution times of every action at 64 MiB (about 2,620 s). The pricing page prices Free, Starter and Professional "per GB-hour" and lists CPU-time pricing only for Business and Enterprise; the separate `actionComputeCpuGbHours` counter is not what those plans pay. The 30-second reply's action ran 30.9 s, which is 0.00054 GB-hours: the 20 included GB-hours cover about 37,000 such replies, and the 1M included calls about 38,000. At Starter prices ($0.33 per GB-hour, $2.20 per million calls) that reply costs about $0.00018 in compute and $0.00006 in calls.
  - **The run outlives the browser on cloud too, but outside the request.** With the client disconnected 6.6 s in, the run kept writing batches and appended the full reply: at 31 s for a 30-second reply, and at 301 s for a 5-minute one, with the scheduled check rescheduling itself every 90 s meanwhile. But Convex recorded `POST /chat` as finished at the disconnect (6.5 s, success), so the rest ran as work left over after the request, which the actions docs say "might or might not complete". A bare probe that only logged showed nothing after the disconnect, because log lines after that point are dropped, and a non-streamed probe was recorded with the error `Client disconnected`. So completion after a disconnect is observed, not promised. If the work is ever cut off, nothing changes in the design: the scheduled check marks the turn `interrupted` about 90 s after the last write, and Try again replaces it. The time after the disconnect was not counted as action compute (only the 6.5 s were); its mutations were counted as calls. A deploy during a run did not stop it.
  - **Time limit: 1,800 seconds**, as the limits page says for the Convex runtime. A streaming probe was stopped at 1,800 s with "Function execution timed out (maximum duration: 1800s)". The client saw an ordinary end of the stream with status 200, not an error, and the handler's cleanup does not run, so a run cut off there would stay `running` until the scheduled check marks it. Interview replies take well under a minute. Stop behaved as built: `turns.stop`, then the next batch is refused and the action marks the run `interrupted` within 1.5 s.
  - **Production redaction: not checked yet, only after the release.** As described in Consequences, with the maintainer's approval: deploy a temporary HTTP action that throws a sentinel error such as `Error("unfold-redaction-sentinel")` without catching it, request it once with `curl -i`, and confirm the body and headers do not contain the sentinel. Check `convex logs --prod` shows the full message, then remove the route with the next deploy. The chat action catches its own errors, so a request to it cannot answer this.

## Changes to earlier ADRs

ADRs are immutable (ADR 0001); these notes record what changes and where.

- **ADR 0003 (BYOK):** the documented hop is now Unfold's Convex HTTP action instead of the Worker route. The rules stay; rule 1 reads "never written to a Convex document, a function argument, a scheduled job, a log …". ADR 0003 and `SECURITY.md` were updated by the chat move (#75).
- **ADR 0005 (deployment):** adds the Convex deploy before the Worker deploy, and a Convex deploy key. The post-deploy smoke test stays.
- **ADR 0008 (Better Auth):** superseded. ADR 0016 replaces it: Convex Auth v2 with Google, required before the first chat. Two parts of ADR 0008 still hold: Google is the sign-up method, and provider keys are never stored by the server.
- **ADR 0011 (testing):** item 3 becomes "the production build with a local Convex backend, no Convex or Cloudflare account". Item 10 (how E2E signs in) is settled by the auth spike (#33) and recorded in ADR 0016.
- **ADR 0012 (interview model):** unchanged, except that "local storage and sync" means Convex.

## Consequences

- Sync, conflict handling, tombstones and per-browser ownership (ADR 0013, "Open for #36") are no longer problems: there is one copy, and Convex pushes changes to every open tab and device.
- Once the browser reads the turn document (not built yet, see "Built in #75"), a reload will no longer lose a round waiting for an answer, or the part of a reply already written to the turn document; ADR 0013 loses both. The server already keeps them. On a local backend an HTTP action keeps running after the browser disconnects, as long as it does not forward the request's abort signal (see "Spike for #75"). On a cloud development deployment it did too, but as work left over after the request, which Convex does not promise to finish (see "Built in #75"). If it stops, the turn document will keep what was written up to the last batch until it is marked `interrupted` (by the action, or by the scheduled check), and the user will press Try again, which replaces it with a new run. A partial reply is never appended as a message.
- Conversations are stored on our server, tied to the user's account. The privacy note and `SECURITY.md` must say so before this ships.
- Once the chat move ships, provider keys will pass through Convex instead of Cloudflare. Users will have to trust that our Convex functions do not log them; self-hosting stays possible.
- The IndexedDB work from #28 is removed. The interview logic, `deriveTree`, the savable-prefix logic, the canvas and the UI stay.
- Development needs a Convex backend: `pnpm dev` runs alongside it (documented in `docs/operations/development.md` when it lands). CI needs one too, local and without secrets.
- One more vendor and one more deploy step. A Convex outage takes the whole app down except static pages.
- Verified since this ADR was written: a local Convex backend in CI and E2E (#82), the TanStack Query integration (#74), and, on a local backend only, `chat()` streaming from an HTTP action in the default runtime, the action outliving a disconnect, and the action reaching aimock (see "Spike for #75").
- Verified on a cloud development deployment on 2026-11-19, with a fake model (see "Built in #75"): the run outlives a disconnect (not guaranteed), the time limit is 1,800 s, action compute is billed on wall-clock time at 64 MiB, and every execution counts as a function call, HTTP actions and preflights included.
- Not yet verified:
  - the same four replies with a real model and a real browser (needs a provider key the maintainer has; Gemini is not supported yet);
  - whether an uncaught error in an HTTP action is redacted in the response, on **production**. Convex documents error details for development deployments and redaction for production ones in general, without mentioning HTTP actions, and on a cloud deployment neither is verified for HTTP actions; so a result on a development deployment does not answer this. The chat action will catch its own errors, so a request to it cannot answer this. It needs a temporary HTTP action that throws a harmless sentinel error, deployed to production only for the check and removed afterwards, with the maintainer's approval.
