# 13. Local-first storage of conversations

- Status: Proposed
- Date: 2026-11-09

## Context

ADR 0012 makes the chat messages the only stored source of truth. The canvas tree is derived from them, node ids are positional (`idea`, `r2q1`), and so the message list must stay append-only. This ADR decides where those messages live in the browser and what shape they have. Sync to D1 (#36) comes later and must stay possible.

What we checked (read 2026-11-09):

- **Web Storage** ([MDN, storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)): the page gives limits of "10 MiB" and "5 MiB per origin" without reconciling them. It is synchronous and per origin. Writes that exceed the limit throw `QuotaExceededError`.
- **IndexedDB quota and eviction** (same page): per-origin limits are a share of disk (Chrome up to 60%, Firefox best-effort the smaller of 10% of disk or 10 GiB, Safari about 60%). Data is best-effort by default and an evicted origin loses all its data at once. `navigator.storage.persist()` asks for exemption; Chromium and Safari decide without a prompt, from the user's history with the site. Safari deletes script-written data when the origin has had no user interaction in the last seven days of browser use, if cross-site tracking prevention is on; the page does not say whether this covers IndexedDB explicitly. For private browsing the page says only that browsers may apply different quotas and that stored data is usually deleted when private browsing ends; it does not name IndexedDB.
- **TanStack AI client persistence** ([API](https://tanstack.com/ai/latest/docs/api/ai-client), [client persistence](https://tanstack.com/ai/latest/docs/persistence/client-persistence)): `indexedDBPersistence()` and custom adapters (`getItem`, `setItem`, `removeItem`) store one `{ messages, resume? }` record per `threadId`. The docs do not say whether a client adapter writes per chunk or per finished turn, who generates `UIMessage.id`, or whether `createdAt` (optional) is set automatically.
- **`idb`** ([README](https://github.com/jakearchibald/idb)): ISC licence, about 1.19 kB brotli. A thin promise wrapper with versioned `upgrade` callbacks and `blocked` / `blocking` handlers. It has no cross-tab change notification. We could not read its npm page, so its current version is unchecked.
- **Cross-tab** ([BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/BroadcastChannel), [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)): both are listed as widely available since March 2022. MDN says Web Locks is limited to secure contexts.

## Decision

### Where: IndexedDB through `idb`

Conversations live in IndexedDB, wrapped by `idb`. localStorage is too small and blocks the main thread. We do not use TanStack's `indexedDBPersistence`: it keeps one blob per conversation, so it has no conversation list or metadata, and its save timing is undocumented. Because it keeps the whole message list under one key, we expect each save to write the whole record (our inference from the adapter interface, not stated in the docs). We feed stored messages to the chat client as initial messages and save through our own functions. How the two connect is decided in #26. We do not store the library's `resume` snapshot, so resuming a half-streamed reply after a reload is not supported.

### What is stored

Two object stores. There is no tree store (ADR 0012).

```ts
type ConversationRecord = {
  id: string; // UUIDv7, generated in the browser
  title: string; // mutable metadata
  schemaVersion: number; // shape of this conversation's message records
  nextSeq: number; // count of stored messages
  createdAt: string; // ISO 8601 UTC
  titleRev: number; // incremented on every title change
  updatedAt: string; // last append or title change, not migration
};

type MessageRecord = {
  conversationId: string;
  seq: number; // 0-based, contiguous; key is [conversationId, seq]
  id: string; // unique within the conversation, stable once saved
  createdAt: string; // ISO 8601 UTC, set by us
  message: UIMessage; // as the chat library produced it
};
```

`seq` is the order and the only thing `deriveTree` may rely on. Ids are not ordered by us, and timestamps come from the browser clock, so neither decides order. Message ids are generated by us as UUIDv7 if the chat library lets us supply the generator, and otherwise are the library's own ids. Whether it does is unverified (#26). Messages are never edited, reordered or deleted individually. The only permitted rewrite is a migration (below), and it keeps `id`, `seq` and the count unchanged. If the chat library turns out to modify a message after we saved it (for example, attaching a tool result), that is an open item for #26. The rule here is that we save a message only once it will no longer change.

The conversation list is sorted by an index on `updatedAt`.

### When we write

Each save is one `readwrite` transaction over both stores that:

1. reads the conversation record;
2. fails if it is missing, if `nextSeq` differs from the value the caller expected, or if `schemaVersion` is newer than this code understands;
3. writes the new messages at `seq = nextSeq …`, then updates `nextSeq` and `updatedAt`.

A title change is a separate transaction with the same missing-record and `schemaVersion` checks. It compares `titleRev` with the value the caller expected, then increments it and updates `updatedAt`. Appends and title changes guard different fields, so they do not conflict with each other.

Creating a conversation is one transaction that writes the first message at `seq = 0` and the record with `nextSeq = 1` and `titleRev = 0` together. A save never recreates a deleted conversation.

We save twice per turn, and never per streamed token:

- the user message (the idea, or the submitted answers) when it is sent;
- the assistant message when its stream completes normally.

We save a completed turn whether or not its tool call is valid. Validation belongs to the validator and `deriveTree` (ADR 0012), which already ignore rejected calls and app-generated correction messages, and positional ids count only valid `ask_round` calls. A stream that errors or is aborted stores nothing for the assistant message. A reload mid-stream loses only that unfinished reply. How the chat resumes after a failed turn is decided in #26, but it must not delete or rewrite stored messages.

### Ids and timestamps

- Conversation ids are UUIDv7. The browser's `crypto.randomUUID()` produces version 4 UUIDs ([Web Crypto, section 10.1.2, Editor's Draft of 22 October 2026](https://w3c.github.io/webcrypto/#Crypto-method-randomUUID), read 2026-11-09), so generating v7 needs a small function or library, chosen when this is built.
- Timestamps are ISO 8601 strings in UTC, written by us (`createdAt`, `updatedAt`). We do not rely on the library's optional `createdAt`.
- `seq` is local order. It is not an identity across devices (see Sync).

### Migrations

- The IndexedDB version carries structural changes in `upgrade`. If another tab holds an older connection, `blocked` tells the upgrading tab to ask the user to close it. The older tab's `blocking` handler closes its connection and asks the user to reload.
- `schemaVersion` on the conversation covers the message shape, including a chat-library upgrade that changes it. A conversation is migrated when it is opened and before any append, in one transaction that rewrites all its messages and bumps the version.
- Migrations are additive and backward compatible where possible, in the spirit of ADR 0009.
- If stored data is newer than the running code (for example after a rolled-back deploy), or a migration fails, we do not write. The conversation is left untouched and the user sees an error. We never overwrite data we do not understand. Whether IndexedDB rejects opening an old version outright is unverified; either way the result must be this behaviour.

### Quota, eviction and unavailable storage

- On the first save we call `navigator.storage.persist()` and report the outcome without promising it. Browsers may decide silently, and even persistent data is removable by the user.
- A failed save (for example `QuotaExceededError`) shows a visible, persistent warning that the conversation is not saved. The conversation keeps working in memory. Unsaved messages are retried in order as one batch after a storage failure (not after a `nextSeq` or `titleRev` conflict, see Several tabs). Because a transaction is all or nothing, a retry cannot duplicate or skip messages. A reload loses whatever is still unsaved, and the warning says so.
- If IndexedDB cannot be opened at all (including private browsing modes that block it, which is unverified), the app runs memory-only with the same warning. We never fall back to localStorage silently.
- Even when IndexedDB opens and accepts writes, a private window may delete it when it closes (MDN says stored data is "usually" deleted). We cannot detect private mode reliably, so the app's storage notice says that conversations in private windows are usually lost when the window closes.
- We never delete conversations automatically to make room.

### Several tabs

The `nextSeq` check on appends and the `titleRev` check on title changes are the guards. If another tab saved first, our save fails, the tab keeps its unsaved messages visible as unsaved, and tells the user the conversation changed elsewhere and must be reloaded. v1 does not merge. If another tab deleted the conversation, the save fails the same way and does not recreate it.

After each committed save or delete, the tab posts `{ conversationId }` on a BroadcastChannel so other tabs refresh early. This is a hint only. A tab that misses it still gets the right answer from the check. We do not use Web Locks in v1, so two tabs can run a model call on the same conversation at once, and the second one to save loses. This is warned about, not prevented.

### Delete and export

Deleting a conversation removes its record and all its messages in one transaction. The user-facing export is the Markdown report from ADR 0012. A raw JSON backup and import is not designed here, because import would have to respect the append-only and id rules. Deletion is local only until sync exists.

### Encryption and keys

Conversation content is stored in plain form. A WebCrypto key would sit in the same browser origin as the data, so it adds little against script access (XSS is handled by the CSP in ADR 0003), and disk protection is the operating system's job. Anyone with access to the browser profile can read the conversations, and the app's privacy note should say so.

Provider API keys are never in this store (ADR 0003). Records hold only messages and conversation metadata, and a test asserts that stored records contain only the fields above. We cannot detect a key a user pastes into a message. Conversation content is never logged.

### Relation to sync (#36)

The browser copy is the working copy. Sync later pushes and pulls the same message lists. This ADR settles only what keeps that possible:

- ids are generated client-side and unique across devices (conversations: UUIDv7), and messages are identified by `(conversationId, id)`, never by `seq`;
- messages are individual records, so sync can store one row per message and stay under D1's 2 MB row limit instead of one blob per conversation (ADR 0009). A single very large message is possible, and sync must handle it;
- records carry `schemaVersion`, so a synced list can be migrated.

Open for #36:

- conflict handling. Two devices that append offline create divergent lists. Merging them would change positional ids (ADR 0012), so interleaving is not allowed, and the policy (for example, forking) is #36's decision;
- deletion semantics. A local delete would otherwise reappear on the next pull, so #36 must define tombstones before sync ships;
- ownership. The local store is per browser, not per account. Nothing here marks a conversation as belonging to a user, so a second person on a shared browser sees the first person's conversations. #36 decides how local conversations attach to an account, and may add a field by migration;
- title is mutable metadata. Locally `titleRev` stops silent overwrites between tabs; merging titles across devices needs its own rule.

## Consequences

- One small dependency (`idb`), our own schema, no coupling to the TanStack persistence format.
- The chat integration is ours to write (#26). Chat tests do not need IndexedDB because storage sits behind a small interface. The real implementation is tested with an IndexedDB test double or in a browser, chosen when it is built. Quota errors, eviction and cross-tab behaviour cannot be reliably reproduced in unit tests.
- Conversations can be lost to eviction, to the user clearing site data, or by the Safari rule above. `persist()` reduces but does not remove this.
- Not yet verified:
  - (#26) whether the chat library lets us supply message ids and whether it changes a message after it has been saved;
  - (#26) how stored messages are passed to the chat client at start-up;
  - IndexedDB behaviour in private browsing in the browsers we support;
  - how IndexedDB reports `QuotaExceededError` in practice (MDN says writes fail with it, not how);
  - the current `idb` version and release date;
  - that Safari's seven-day rule applies to IndexedDB.
